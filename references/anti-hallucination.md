# 反编造规则（Anti-Hallucination）

投标文件里的一句假话，代价可能是**废标、列入黑名单、甚至合同诈骗**。
这不是"写作风格"问题，是**法律风险**问题。

本文件定义：什么绝对不能写、不确定时怎么写、以及如何收敛一堆 `[待确认]`。

---

## 一、绝对禁止编造的六类内容

### 1. 技术参数
型号、版本、吞吐、并发、时延、容量、分辨率、精度、功耗、MTBF/MTTR。

> ❌ "系统单机支持 5000 路并发接入，时延低于 50ms。"
> ✅ "系统单机支持 `[待确认: 需原厂 datasheet 确认最大并发数]` 路并发接入，端到端时延 `[待确认]`。"

**为什么**：参数一旦写入，就是合同技术指标。达不到即违约，且评委可能要求现场验证。

### 2. 业绩与案例
客户名称、项目名称、合同金额、上线时间、验收结论、用户评价。

> ❌ "我方曾为某省级公安厅建设同类平台，合同额 3200 万元。"
> ✅ "我方具备同类项目建设经验 `[待确认: 需从业绩库调取，附合同关键页与验收报告]`。"

**为什么**：业绩是评分项，也是核查项。伪造业绩属于提供虚假材料谋取中标，法定后果严重。

### 3. 资质与证书
ISO/CMMI 等级、软著登记号、检测报告编号、原厂授权、行业资质。

**规则**：只写**证书上原文的名称和编号**，等级不加不减。证书过期或尚未取得，写"正在办理"都是风险，应改为不写或如实说明。

### 4. 人员信息
姓名、职称、执业资格、证书编号、从业年限、社保关系。

**规则**：只写已确认在册人员。**不要为了凑"项目经理具备 PMP"而虚构**——评标可能要求提供证书原件与社保记录。

### 5. SLA 与服务承诺
响应时限、到场时间、修复时限、备件到货、可用性百分比、赔付标准。

> ❌ "7×24 小时服务，15 分钟响应，2 小时到场，4 小时修复。"
> ✅ "提供 7×24 小时服务支持 `[待商务确认: 响应/到场时限需服务部门核定，写入即构成合同义务]`。"

**为什么**：SLA 是最容易被写得太漂亮、又最难履约的部分。写"2 小时到场"却没覆盖到项目所在地的地市，就是给自己埋雷。

### 6. 测试与验证结论
POC 结果、压测数据、第三方检测、兼容性认证。

**规则**：没有报告就不写结论。有报告只写报告里有的指标，不外推。

## 二、不确定时的三种合法写法

| 情形 | 写法 | 后续动作 |
|---|---|---|
| 需外部材料确认 | `[待确认: 需 XX 材料]` | 进待补清单，指定责任人 |
| 需商务/决策人拍板 | `[待商务确认: 拟 XX，需批准]` | 进决策清单，投标前必须清零 |
| 属行业通识、无具体数值 | `[通识表述，需技术确认]` | 技术负责人复核后删除标记 |

**统一格式**：`[待确认: 原因]`，全角冒号，不换行，便于脚本正则匹配。
`validate_bid.py` 会抓 `[待确认`、`TODO`、`XXX`、`待补充`、`____`、`？？` 等标记，**交付前必须清零**。

## 三、允许推断的边界

可以写（属通用工程常识，不含具体承诺）：

- "采用双机热备架构可降低单点故障风险"
- "支持标准 SNMP 协议，可接入主流网管平台"
- "遵循 GB/T 28181 联网标准"（若产品确有该认证，需核实后保留）

不可以写（看似常识，实则含具体承诺或需资质）：

- "满足等保三级要求"——需要测评报告支撑，不能凭架构推断
- "完全兼容现有系统"——兼容性需测试证明
- "符合国家信创目录要求"——需在目录内，非自证
- "零故障运行"——物理上不可能，属虚假宣传

**判据**：这句话如果被评委追问"证据呢"，你能立刻拿出材料吗？拿不出，就得改写法。

## 四、`[待确认]` 的收敛流程（交付前必走）

```
1. 全量导出     validate_bid.py --list-todo  → 得到全部标记及所在章节
2. 分类归口     技术 / 商务 / 资质人事 / 原厂 / 项目管理
3. 指派责任人   每类指定一个对口人（不是"投标组"，要具体到人）
4. 设截止时间   内部截止必须早于投标截止 ≥ 2 个工作日（留装订时间）
5. 逐条回填     回填时同步更新 requirements.csv 的 response_type
6. 二次校验     重跑 validate_bid.py，确认标记清零
7. 兜底         实在无法确认的，改写为不含承诺的表述，而非保留标记交付
```

**红线**：带 `[待确认]` 标记的文件**不得作为最终版提交**。若时间不足，只能删去该表述改写，不能带着标记交付——那是把内部问题暴露给评委。

## 五、发现已写内容有误时的处理

| 阶段 | 处理 |
|---|---|
| 尚未提交 | 直接改，同步更新台账，记录变更 |
| 已提交未开标 | 依招标文件"修改与撤回"条款办理，通常需书面通知并在截止前送达 |
| 已开标 | 不得擅自更正，按澄清程序处理；涉及实质性内容的错误应主动向招标方报告 |
| 已中标 | 立即内部报告，评估是否构成缔约过失，由法务介入 |

**原则**：错误越早暴露，代价越小。**隐瞒错误的风险远大于承认错误。**

## 六、给 AI 使用者的提醒

用 AI 生成投标内容时，最容易出的不是"文笔差"，而是**流畅的编造**——
模型会把不存在的参数写得像真的，因为它"读起来合理"。

因此使用本技能时必须坚持：

1. **输入即边界**：只把已确认的材料喂给模型，不要让它在空白处发挥；
2. **输出必复核**：AI 产出的每个数字、每个名称，都要回到原始材料核对一遍；
3. **标记不省略**：宁可满篇 `[待确认]`，也不要满篇"看起来对"的假数据；
4. **责任在人**：AI 是起草工具，签署人承担全部法律后果。

## 七、复用污染：最容易被忽视的"编造变体"（v2 新增）

复用上一份标书时，编造往往不是"凭空写"，而是**旧内容没删干净**：

| 污染类型 | 表现 | 检测方式 |
|---|---|---|
| 旧项目名残留 | 封面改了，页眉/正文第 3 节还写着上个项目 | 脚本 `--project` 比对，命中非本项目名称即报 |
| 旧招标编号残留 | "项目编号：KM-2026-0901" 出现在无关段落 | 脚本比对 `--project-no` |
| 旧客户名残留 | 案例段落里出现上一个业主单位 | 人工 + 关键词表 |
| 旧参数残留 | 上一项目是 2000 路，本项目 500 路，正文仍写 2000 | 台账数值比对（人工必做） |
| 内部用语残留 | "内部""我司内部口径""待领导定""按上次模板" | 脚本内置词表 |
| 模板提示语残留 | "此处填写""示例：""XXX 公司" | 脚本 TODO/占位符检查 |

**为什么它比凭空编造更危险**：凭空编造的假数据往往一眼能看出突兀；
旧内容残留则**读起来完全通顺**，评委也未必发现，直到资格性审查时因为项目名不一致被废标。

**三条纪律**：

1. 复用 → 先跑 `validate_bid.py --project "<本项目名>" --project-no "<编号>"`，再逐节改；
2. 案例段落复用 → 只复用**结构**与**写法**，主体、规模、时间必须换成本项目真实信息；
3. 无法替换的旧案例 → 整段删除，不要"改个名字充数"（业绩造假在评审中可直接否决）。

## 八、`[待确认]` 的收敛优先级（v2 新增）

待确认项多的时候不要按出现顺序处理，按**后果**排序：

| 优先级 | 判定 | 例子 | 处理方式 |
|---|---|---|---|
| P0 | 落在 `mandatory=Y` 条目上 | 资质证书编号、接入能力、工期 | 必须拿到书面依据，否则改写为不含该承诺的表述 |
| P1 | 落在评分点上 | 业绩数量、认证等级、团队人数 | 能拿证据就写，拿不到就标"该项预计不得分" |
| P2 | 仅影响表达细节 | 术语统一、单位写法 | 统一口径即可，不必等外部确认 |
| P3 | 属于背景描述 | 行业趋势、公司简介 | 直接删掉，不要为它等材料 |

**经验数字**：真实项目收敛完后，P0 必须为 0；P1 允许残留但要在交付说明中逐条列出；
P2/P3 不允许出现在最终稿——它们不影响得分，只增加暴露风险。
