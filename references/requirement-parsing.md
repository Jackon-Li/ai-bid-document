# 招标要求抽取口径（Requirement Parsing）

目的：把一份几十页的招标文件，变成一张**可勾选、可计数、可追溯**的要求台账。
台账错了，后面全错——这是整个流程里最不能省的一步。

---

## 一、抽取单位：一句话一条要求

判定标准：**能独立回答"满足 / 不满足"的最小单元**。

| 原文 | 抽取结果 | 说明 |
|---|---|---|
| "系统应支持不少于 2000 路视频接入，并支持级联扩展。" | 拆成 2 条：①接入 ≥2000 路；②支持级联扩展 | 两个可独立判定的点 |
| "投标人应提供原厂授权书、售后服务承诺函及三年质保。" | 拆成 3 条 | 三份材料，缺一即不满足 |
| "系统应具备良好的可扩展性。" | 1 条，`type=技术`，`mandatory=N` | 无法量化，归为评分项而非门槛项 |

**不要做的事**：把一整段抄成一条。一条里塞三个条件，评标时无法逐条核对，等于自己放弃可核对性。

---

## 二、强制词的判定（决定 mandatory）

中文招标文件靠情态动词表达强制程度，判错直接导致废标风险被低估。

| 关键词 | 强度 | mandatory | 说明 |
|---|---|---|---|
| 必须、须、应、不得、严禁、禁止 | 强 | `Y` | 不满足通常即否决/废标 |
| 不低于、不少于、不高于、最多、至少 | 强 | `Y` | 门槛值，低于即不响应 |
| 需提供、应提供、须提交、附 | 强 | `Y` | 材料类硬要求 |
| 建议、宜、可、鼓励 | 弱 | `N` | 影响得分或不影响 |
| 优先、择优 | 弱 | `N` | 评分倾向 |
| 如有、若……则 | 条件 | 视条件 | 需判断本包是否触发 |
| 原则上、一般情况下 | 弱化 | `N` | 通常留了变通口，但要记录 |

**陷阱**：同一个词在不同章节强度可能不同。"投标人应……"出现在"投标人须知"里通常是废标项；出现在"技术方案编制建议"里可能只是格式要求。**判定时看所在章节，不只看词。**

---

## 三、五个必须单独成表的类别

这五类混在技术条目里，是漏项的主要来源：

### 1. 资格条件（`type=资格`）
营业执照、资质证书、财务报告、社保、纳税、无重大违法记录声明、联合体协议。
→ 这类是**准入门槛**，缺一项直接出局，与方案写得好不好无关。**优先全部抽完再动笔。**

### 2. 符合性/格式要求（`type=格式`）
份数（正本 X 份副本 Y 份）、装订方式、密封与标记、签字盖章位置、页码、目录、电子版格式（U 盘/平台上传）、投标函格式、报价表格式。
→ 这类最容易被当成"形式问题"忽略，但它是**废标高发区**。

### 3. 技术规格（`type=技术`）
功能、性能、接口、协议、兼容性、容量、扩展性、可靠性指标。
→ 抽取时**必须保留原始数值和单位**，不要做换算。换算留到应答阶段。

### 4. 商务条款（`type=商务`）
工期/交货期、付款方式与比例、履约保证金、质保期、违约责任、知识产权归属、保密要求。
→ 这类条款决定**能不能签**，不是能不能中。抽取时标记 `需商务决策=Y`。

### 5. 服务与实施（`type=服务`）
实施组织、项目团队、培训、文档交付、验收标准、售后响应时限、备件、驻场。

## 四、评分办法的抽取（单独处理）

评分办法不是"要求"，是"计分规则"，不能混进 `requirements.csv` 的 mandatory 逻辑里。

抽取字段：

| 字段 | 含义 |
|---|---|
| `score_item` | 评分项名称（如"类似项目业绩"） |
| `score_max` | 该项满分 |
| `score_rule` | 计分规则原文（如"每提供 1 个得 1 分，最多 5 分"） |
| `evidence` | 需要什么材料才能得分 |
| `our_capability` | 我方能否满足（高/中/低/无） |
| `owner` | 由谁提供材料（技术/商务/原厂/人事） |

**关键动作**：算一遍"理论满分"与"我方可达分"，差额就是**必须补的短板**。
这个差额要单独汇报，它比"方案写得好不好"更影响中标概率。

## 五、抽取质量自检（S1 结束时必做）

回答这五个问题，任何一个答不上来就不能进入 S2：

1. **总数是多少？** 总条目数 / mandatory=Y 条数 / 各 type 分布——说得出具体数字吗？
2. **门槛项都在吗？** 资格、格式、废标条款是否已 100% 抽取？抽查任意 3 条原文能否在台账里找到？
3. **原文摘录忠实吗？** `source_quote` 是否为原文照抄（含错别字）？改写过的摘录无法用于复核。
4. **模糊项标出来了吗？** 招标文件里表述含糊、前后矛盾的条目，是否单独标记 `需澄清=Y`？
5. **歧义有没有登记？** 需要向招标方提问澄清的问题，是否形成了澄清函清单？

> 第 5 点常被跳过。**澄清函是投标人的合法权利**，也是把模糊要求变确定要求的唯一机会。错过澄清截止时间，模糊条款就变成"评委说了算"。

## 六、常见矛盾与处理方式

| 矛盾类型 | 例子 | 处理 |
|---|---|---|
| 前后不一致 | 第 3 章要"≥2000 路"，第 7 章要"≥3000 路" | 按**更严**的响应，并在澄清函中提问 |
| 技术与商务冲突 | 技术要 60 天交付，商务写 45 天工期 | 按**更短**的响应，标注风险 |
| 要求超出常识 | 要求"7×24 现场驻场 3 年"但预算明显不足 | 按字面响应 + `[待商务确认]` 标注成本风险 |
| 指定品牌/型号 | "或同等" / 直接指名 | 指名则必须响应或提偏离；"或同等"需准备等同性证明材料 |
| 评分项无法达成 | 要求 5 个同类业绩，我方只有 2 个 | 不伪造，改从"单项规模""关联领域"角度争取部分分 |

**原则**：矛盾不自行消解。**登记矛盾 + 按严响应 + 提澄清**，三步都要留痕。

## 七、强制强度五级（v2 新增，替代原来的 Y/N 二分）

`mandatory` 只有 Y/N 两个值，无法排序整改优先级。v2 增加 `strength` 列，与 `mandatory` 并存：

| strength | 判定词 | mandatory | 处理优先级 |
|---|---|---|---|
| `禁止` | 不得、严禁、禁止、不允许、不接受 | Y | P0，反例即废标 |
| `必须` | 必须、须、应（强语境）、不低于/不少于 | Y | P0，缺即废标 |
| `应` | 应（弱语境）、需提供、须提交 | Y | P1 |
| `宜` | 宜、建议、优先、鼓励 | N | P2，影响得分 |
| `可` | 可、允许、如有、视情况 | N | P3，通常仅登记 |

判定规则：

1. **先看词，再看章节，冲突时取更严**：同一句里出现"应…不得…"→ 取 `禁止`。
2. **陈述句也能是强制**："合同签订后 60 日内交货"没有情态动词，但它是硬约束 →
   人工补 `mandatory=Y, strength=必须`，并在 `note` 写"陈述句补标"。
3. **`宜` 不等于可忽略**：评分办法里"宜"往往对应 2–5 分，`status` 标 `待响应` 而非 `无需响应`。

## 八、去重与合并（v2 新增）

真实招标文件同一要求常出现 2–4 次（须知一次、技术规格一次、合同草案一次）。
不去重 → 必答数虚高 → 覆盖率永远算不准 → "已全覆盖"变成自我安慰。

判定为重复的条件（满足任一）：

- 归一化后（去空白/标点/序号）**完全相同**；
- 归一化后相似度 ≥ 0.90，且 `type` 相同；
- 后者是前者的子集（如"提供三年质保" ⊂ "提供三年质保及 7×24 响应"）。

处理方式：

| 情况 | 处理 |
|---|---|
| 完全重复 | 保留首次出现为主条，后续条 `dup_of=R-00X`，`status=重复合并` |
| 后者更严 | 以**更严**的那条为主条，另一条 `dup_of` 指向它，`note` 记"原条目要求 X" |
| 章节不同但语义相同 | 保留两条，`dup_of` 互指，`note` 记"跨章节重复，均需落点" |

**必答数统计口径**：只统计 `dup_of` 为空的主条。报告里同时给出
`原始条目数 / 去重后主条数 / 必答主条数` 三个数字，避免口径争议。

## 九、溯源字段（v2 新增，落实"100% 溯源"）

v1 的 `source_quote` 与 `requirement` 是同一句，等于没有独立溯源。v2 要求：

| 字段 | 取值 | 用途 |
|---|---|---|
| `source_quote` | 原文**逐字照抄**（可含错别字、可跨句） | 复核时逐字比对 |
| `line_no` | 原文行号；.docx 用段落序号（脚本可产出） | 秒级定位 |
| `source_ver` | `v1` / `补遗-01` / `答疑-02` | 版本追溯，防止按旧版写作 |
| `section` | 章节号 + 标题 | 人对人沟通时定位 |

**检验方法**：随机抽 3 条，让没参与的人凭 `source_ver + section + line_no` 找原文，
30 秒内找不到，说明溯源不合格。

## 十、类型判定的优先级（v2 修正 v1 的误判）

v1 逻辑是"先看章节名，再看句内关键词"，导致"投标人须知"整章被默认为资格、
"技术要求"整章被判技术，资格与格式类条款大量误分类。

v2 改为**句内优先、章节兜底**：

```
① 句内出现明确类别词（营业执照/密封/付款/售后/得分…）→ 按该类别
② 句内无线索 → 用所属章节标题判断
③ 章节也无线索 → 按所在章节主体归类，note 标"类型待人工确认"
```

例外：**章节标题本身是强信号时优先**——"评标办法""合同条款"这两章内，
即使句内出现技术词，也不判为 `技术`（避免评分项被写进技术方案）。

人工复核重点：`type` 判错不影响废标，但会让 owner 派错人（资格给技术部、格式给商务部），
交接时最容易在这里断链。
