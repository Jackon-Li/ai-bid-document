# ai-bid-document · AI 投标文档技能

> 把招标文件当作唯一事实来源，把投标文件当作逐条账本。
> **不漏项、不越界、可核对、可交付。**

一个面向**系统集成招投标 / 售前场景**的工作方法与工具集。它不教你怎么"把方案写得漂亮"，
它解决的是投标里真正要命的三件事：**要求有没有漏、参数有没有编、承诺有没有越界**。

适用于 Claude Code、WorkBuddy、Cursor 等支持 Skill / 自定义指令的 AI 编程助手，
也可以完全脱离 AI 当纯方法论与脚本工具使用。

> **中文别名 / 搜索关键词**：投标文档技能、标书写作、售前方案、售前支持、技术标、商务标、
> 招投标、投标文件、点对点应答表、技术偏离表、废标项核查、招标文件解析、spec docs 逐条应答。
> 仓库英文名为 `ai-bid-document`（GitHub 不支持中文仓库名与中文 topics），中文检索请依赖本行。

## 解决什么问题

投标文件写砸，通常不是因为不会写，而是因为这四类事故：

### 事故一：漏项

招标文件 60 页，要求散落在"投标人须知""技术要求""商务条款""评分办法"里。
人工通读三遍仍会漏——尤其**格式类要求**（正本几份、怎么密封、哪里盖章），
它们往往夹杂在不起眼的段落里，但漏一条就是废标。

> 真实代价：方案写了 200 页，因为投标函格式自行修改被判无效。

### 事故二：编造

AI 写方案时最危险的不是文笔差，而是**把不存在的参数写得像真的**。
"支持 5000 路并发、时延低于 50ms"——读起来完全合理，但没有任何出处。
这句话写进标书就是合同技术指标，达不到即违约。

> 真实代价：投标时承诺的参数，验收时无法复现，陷入整改或索赔。

### 事故三：承诺失控

销售在标书里写"7×24 小时 15 分钟到场""免费提供 3 年驻场工程师"，
中标后发现服务网点根本覆盖不到项目所在地，或三年人力成本远超利润。

> 真实代价：低价中标 + 过度承诺 = 项目亏损。

### 事故四：答非所问

招标问"是否支持国密算法"，方案答了一段"我们高度重视信息安全，采用纵深防御理念"。
评委按评分表找分，找不到就不给分——**你没答，等于没写**。

> 真实代价：技术分被压到及格线以下，明明产品满足却输给对手。

**本技能把这四类事故变成四个可检查的机制**：条目化台账、零发明标记、承诺三档分级、覆盖声明。

## 核心设计：五条铁律

这五条是本技能与"通用写作提示词"的根本区别。

| # | 铁律 | 含义 | 防的事故 |
|---|---|---|---|
| 1 | **条目化**：无编号不落笔 | 招标每条要求都有 `R-XXX` 编号，全文只引用编号 | 漏项 |
| 2 | **零发明**：查不到就标待确认 | 参数/业绩/资质/SLA 一律不编，写 `[待确认: 原因]` | 编造 |
| 3 | **覆盖优先**：先答全，再答好 | 覆盖所有必答项 → 才优化表达 | 漏项 |
| 4 | **结构对齐**：不改招标方骨架 | 章节层级、编号、顺序与招标一致 | 答非所问 |
| 5 | **承诺可控**：不写无权承诺 | 承诺分 A/B/C 三档，C 档需决策人批准 | 承诺失控 |

> 五条铁律的完整定义见 [`SKILL.md`](SKILL.md)。

## 功能特性

### 一、要求抽取与台账

把招标文件变成可勾选、可计数、可追溯的 `requirements.csv`。

- 自动识别章节结构：`第X章`、`1.1`、`2.3.1`、`（一）`、Markdown 标题
- 自动判定强制程度：区分"必须/须/应/不得"（废标项）与"建议/宜/可"（评分项）
- 自动归类：资格 / 格式 / 技术 / 商务 / 服务 / 评分 六类
- 自动标记需澄清的模糊表述（"或同等""原则上""视情况"）
- **防误判处理**：不会把"故障响应时间"的"应"、"投标人须知"的"须"误判为强制词

### 二、章节映射与覆盖门禁

`outline-map.csv` 把每条要求安排到具体章节，形成硬门禁：

- 必答条目未映射章节 → **不允许进入撰写阶段**
- 撰写时每章开头写覆盖声明 `> 覆盖条目：R-005, R-006`
- 校验时反向检查：每条必答是否真的被引用

### 三、反编造规则

六类内容绝对禁止编造，并给出"不确定时怎么写"的三种合法格式：

| 情形 | 写法 |
|---|---|
| 需外部材料确认 | `[待确认: 需原厂 datasheet 确认最大并发数]` |
| 需商务决策 | `[待商务确认: 拟承诺 XX，需批准]` |
| 行业通识、无具体数值 | `[通识表述，需技术确认]` |

配套 `--list-todo` 清单模式，交付前必须清零。

### 四、自动校验

两个纯标准库脚本，无需安装依赖：

```bash
# 有阻断项 → 退出码 1；全部通过 → 退出码 0，可直接接入 CI
python scripts/validate_bid.py --bid ./bid --req requirements.csv --map outline-map.csv
```

检查 7 项：占位符残留、必答覆盖率、灰色响应表述、章节映射缺失、
一级章节跳号、绝对化表述、注水套话。

### 五、方法论文档

不是泛泛的"写作建议"，是可直接执行的判定规则：

| 文档 | 内容 |
|---|---|
| [`requirement-parsing.md`](references/requirement-parsing.md) | 一句话一条要求的判定标准、强制词强度表、五个必拆类别、矛盾处理 |
| [`anti-hallucination.md`](references/anti-hallucination.md) | 六类禁编内容、三种合法写法、`[待确认]` 收敛七步流程 |
| [`writing-style.md`](references/writing-style.md) | 先响应后展开的固定句式、禁用词表、承诺三档分级、篇幅控制 |
| [`scoring-matrix.md`](references/scoring-matrix.md) | 评分办法拆解、得分点作战表、主观分三层拿分逻辑、正偏离纪律 |
| [`compliance-checklist.md`](references/compliance-checklist.md) | 7 部分 60+ 项交付前核对清单，标注高频废标点 |
| [`tech-domains.md`](references/tech-domains.md) | 9 大子系统（网络/机房/服务器存储/安防/音视频/布线/软件/安全/运维）要点与评委常问 |

### 六、模板与示例

- `requirements.csv` / `outline-map.csv`：可直接改用的台账模板
- `response-matrix.md`：点对点应答表（含三值响应规范）
- `deviation-table.md`：技术/商务偏离表（含重点条款逐项确认表）
- `delivery-checklist.md`：交付清单（含输入材料、过程产物、待确认收敛、签署递交）
- `examples/walkthrough.md`：从招标文件到交付物的完整演示，带真实命令输出

## 工作流总览

```
S0 建档          确认输入清单（招标文件/评分办法/须知/资格/产品资料/承诺授权）
  │               缺项先出「材料缺口清单」，不猜、不阻塞
  ▼
S1 解析          招标文件 → requirements.csv（R-001 起，逐条编号）
  │               产出基准数字：总条目 N / 必答 M
  ▼
S1.5 人工修订     修正 mandatory 判定、补 owner、整理澄清函
  │               ⚠️ 这一步不能省，脚本只做初判
  ▼
S2 映射          每条要求 → 具体章节（outline-map.csv）
  │               🚧 硬门禁：必答未映射 → 禁止撰写
  ▼
S3 撰写          逐章推进，每章首部写覆盖声明，首段直接回应原文
  │               不确定处标 [待确认]，不编造
  ▼
S4 校验          validate_bid.py 跑 7 项检查
  │               BLOCKER 必须清零；WARN 人工判断
  ▼
S5 交付          7 件套：正文/台账/映射/应答表/待确认清单/交付清单/校验报告
                  汇报写清「已完成什么、未完成什么、哪些待确认」
```

## 安装

### 方式一：作为 Skill 使用（Claude Code / WorkBuddy / Cursor）

把整个目录放到用户级 skills 目录：

```bash
# Windows
mv ai-bid-document "%USERPROFILE%\.workbuddy\skills\"

# macOS / Linux
mv ai-bid-document ~/.workbuddy/skills/
```

重启助手后，提到"投标 / 标书 / 招标文件 / 应答表 / 偏离表"等关键词时会自动加载。

需要放在项目内共享时，改放到 `{项目目录}/.workbuddy/skills/`。

### 方式二：脱离 AI 当工具用

只需要 Python 3.8+，无第三方依赖：

```bash
git clone https://github.com/Jackon-Li/ai-bid-document.git
cd ai-bid-document
python scripts/extract_requirements.py --help
```

读取 `.docx` 需额外安装（可选）：

```bash
pip install python-docx
```

## 快速开始

### 五分钟上手

**第 1 步：抽取要求**

```bash
python scripts/extract_requirements.py --input 招标文件.txt --output requirements.csv
```

看到这样的输出就成功了：

```
生成条目数 : 22
必答(Y)    : 17   非必答(N): 5
按类型分布：
  资格: 4    格式: 3    技术: 5    商务: 4    服务: 3    评分: 3
```

**第 2 步：人工修订台账（关键，不能跳）**

打开 `requirements.csv`，重点改三件事：

1. 把陈述句形式的强制条款改成 `mandatory=Y`
   （如"合同签订后60日内交货"没有情态动词，脚本抓不到）
2. 把评分项从 `Y` 改回 `N`（不满足不废标，只是少得分）
3. 补齐 `owner` 列，每条都要有责任人

改完记住两个数字：**总条目数 / 必答数**。这是后面所有覆盖率计算的基准。

**第 3 步：写章节映射**

复制 `templates/outline-map.csv`，为每条必答安排章节。

**第 4 步：撰写时随时查待确认项**

```bash
python scripts/validate_bid.py --bid ./bid --list-todo
```

**第 5 步：交付前校验**

```bash
python scripts/validate_bid.py --bid ./bid --req requirements.csv --map outline-map.csv
```

`exit 0` 才可交付。看到 `exit 1` 就按报告逐项清零。

> 完整演示见 [`examples/walkthrough.md`](examples/walkthrough.md)。

## 两份核心台账

整个方法的地基是两张表。理解这两张表，就理解了这个技能。

### 1. `requirements.csv` — 要求台账

**作用**：回答"招标方到底要求了多少件事，每件是什么"。

| 字段 | 含义 | 为什么重要 |
|---|---|---|
| `req_id` | `R-001` 起的唯一编号 | 后续所有引用、核对、校验都靠它 |
| `section` | 来源章节 | 追溯时能立刻翻回原文位置 |
| `requirement` | 要求正文 | 写作时的直接依据 |
| `type` | 资格/格式/技术/商务/服务/评分 | 决定由谁负责、怎么响应 |
| `mandatory` | `Y` = 不满足即废标 | **最高优先级字段**，判错代价最大 |
| `source_quote` | 原文摘录 | 复核时逐字对照，防止改写走样 |
| `response_type` | 响应/偏离/证明/承诺 | 决定这一条在标书里以什么形式出现 |
| `need_clarify` | `Y` = 需发澄清函 | 把模糊要求变确定要求的唯一机会 |
| `owner` / `status` | 责任人 / 状态 | 多人协作时不至于互相等 |

### 2. `outline-map.csv` — 章节映射

**作用**：回答"每条要求安排在哪一章答"。

| 字段 | 含义 |
|---|---|
| `req_id` | 对应要求 |
| `chapter` | 章节号（如 `3.2`） |
| `chapter_title` | 章节名称 |
| `primary` | `Y` = 主应答章节（一条要求可有多处提及，但只有一个主应答） |
| `evidence_needed` | 需要的证明材料 |

**它是硬门禁**：存在未映射的必答条目时，不允许开始撰写。
因为"边写边想放哪"是漏项的主要成因。

## 适用场景

### ✅ 强烈建议使用

| 场景 | 为什么适合 |
|---|---|
| **系统集成项目投标** | 子系统多、要求分散、格式要求繁杂，正是条目化的用武之地 |
| **政府/国企采购投标** | 资格与符合性审查严格，废标风险高，格式清单价值最大 |
| **技术标撰写** | 需逐条对应评分表，"先响应后展开"直接提升主观分 |
| **点对点应答表 / 偏离表编制** | 三值规范（完全响应/部分响应/不响应）避免灰色表述 |
| **多轮投标 / 复用历史标书** | 台账可沉淀为组织资产，下次直接改 |
| **多人协作投标** | 台账带 owner 与 status，交接不丢信息 |
| **投标文件复核** | 已有稿件直接跑校验，快速发现漏项与占位符残留 |
| **用 AI 辅助写标书** | 反编造规则正是 AI 最需要的外部约束 |

### ⚠️ 需要调整后使用

| 场景 | 需要注意 |
|---|---|
| **货物类纯采购**（无实施） | 技术方案权重低，重点放在应答表与偏离表，可跳过 S3 的大段撰写 |
| **服务类采购**（咨询/外包） | 需补充"人员投入测算""服务方法论"相关内容 |
| **工程类招标**（施工） | 本技能偏 IT 集成，工程量清单、施工组织设计需另配专业模板 |
| **国际招标 / 英文标书** | 词表为中文招标文件设计，英文需替换 `STRONG_PATTERNS` 等词表 |

## 不适用场景

明确说明边界，避免误用：

| 不适用 | 原因 |
|---|---|
| 无招标文件、仅凭一句话自由创作方案 | 缺少"唯一事实来源"，条目化无从谈起。请用通用方案写作 |
| 报价测算、成本与利润率推算 | 需财务口径与内部成本数据，本技能不介入 |
| 判断"这个项目该不该投" | 属商务决策，不由工具输出结论 |
| 代签、代盖章、伪造资质与业绩 | **明确拒绝**。这已超出工具范畴，涉及违法 |
| 承诺授权、法律条款确认 | 必须由投标决策人与法务签署确认，AI 无权代决 |

## 设计思路

几处刻意的取舍，说明为什么这样设计：

### 为什么不直接让 AI 写整份标书？

因为 AI 最擅长的是"生成流畅文本"，而投标最怕的正是"流畅但不可靠"。
一份 200 页的 AI 生成标书，人工复核成本可能高于自己写——
你要核对每个数字、每个案例、每个承诺。

所以本技能把 AI 放在**该在的位置**：做机械的抽取、归类、校验、格式转换，
把判断留给人。这也是 `mandatory` 判定必须人工复核的原因。

### 为什么强制"条目化"而不能直接对段落？

因为**段落无法计数**。你无法回答"这版比上版多覆盖了几个要求"，
也无法在交接时说"还有 3 条没答"。
编号把模糊的"应该写得差不多了"变成明确的"17/18 已覆盖，R-019 缺"。

### 为什么校验脚本只查形式？

因为语义级检查（答非所问、数值方向错误）误报率极高，
一个天天误报的工具会被弃用。
所以脚本只做**确定性检查**——占位符、覆盖率、编号、词表，
把语义判断交给 `compliance-checklist.md` 的人工流程。

**脚本管形式，清单管实质。** 两者都不能省。

### 为什么把"承诺"单独分级？

因为投标文件是**要约文件**，写入即产生法律约束。
技术人员写方案时容易把"我们能做"写成"我们承诺无条件做到"，
而这两者在合同上的分量完全不同。
三档分级（A 可自主 / B 需部门核定 / C 需决策人批准）把这个问题前置到写作时解决，
而不是等中标后发现承诺无法履约。

## 常见问题

**Q：这套方法适合小项目吗？会不会太重？**

A：项目越小，资格与符合性要求占比越高，反而越不能漏。但可以简化：
只做 `requirements.csv` + 跑 `validate_bid.py`，跳过 mapping 与完整清单。
核心是"条目化 + 校验"，其余可按需取用。

**Q：抽取出来的条目太多，几百条怎么办？**

A：正常。真实招标文件 60 页通常 100–300 条要求。
关键是**必答（mandatory=Y）的条数**，那才是硬约束，通常只占 40%–60%。

**Q：脚本判定错了怎么办？**

A：改 CSV。脚本只是初稿工具，`requirements.csv` 是活文档，
人工修订后的版本才是准的。修订记录建议写进 `note` 列。

**Q：能让 AI 直接把整份标书写完吗？**

A：技术上可以，但**不建议直接交付**。
合理用法：AI 按章节起草 → 人工核对每个数字与承诺 → 脚本校验形式 → 清单核对实质。
把 AI 当"高速打字员 + 结构检查员"，不当"决策者"。

**Q：没有评分办法怎么办？**

A：S2 只做章节映射，跳过得分点作战表。
但强烈建议向招标方索取或从招标文件中找——**没有评分办法，等于闭着眼睛写方案**。

**Q：`[待确认]` 太多，来不及收敛怎么办？**

A：两条路：① 优先收敛 `mandatory=Y` 条目里的标记（这些影响废标）；
② 实在无法确认的，**删去该表述改写为不含承诺的写法**，而不是带标记交付。
带标记交付等于把内部问题暴露给评委。
