> 把招标文件当作唯一事实来源，把投标文件当作逐条账本。
> **不漏项、不越界、可核对、可交付。**

一个面向**系统集成招投标 / 售前场景**的工作方法与工具集。它不教你怎么"把方案写得漂亮"，
它解决的是投标里真正要命的三件事：**要求有没有漏、参数有没有编、承诺有没有越界**。

适用于 Claude Code、WorkBuddy、Cursor 等支持 Skill / 自定义指令的 AI 编程助手，
也可以完全脱离 AI 当纯方法论与脚本工具使用。

**当前版本 v2.0.0** —— 在 v1 的"条目化 → 映射 → 撰写 → 校验 → 交付"闭环上，
补齐了**模式路由、投标决策辅助、评分作战表、双轨核查、复用污染扫描、机器可读报告**六块能力，
并修掉 10 个会让"看起来通过、其实没做"的脚本缺陷（详见 [v2 修了什么](#v2-修了什么)）。

## 解决什么问题

投标文件写砸，通常不是因为不会写，而是因为这四类事故：

### 事故一：漏项

招标文件 60 页，要求散落在"投标人须知""技术要求""商务条款""评分办法"里。
人工通读三遍仍会漏——尤其**格式类要求**（正本几份、怎么密封、哪里盖章），
它们往往夹杂在不起眼的段落里，但漏一条就是废标。

> 真实代价：方案写了 200 页，因为投标函格式自行修改被判无效。

### 事故二：编造

AI 写方案时最危险的不是文笔差，而是**把不存在的参数写得像真的**。
"支持 5000 路并发、时延低于 50ms"——读起来完全合理，但没有任何出处。
这句话写进标书就是合同技术指标，达不到即违约。

> 真实代价：投标时承诺的参数，验收时无法复现，陷入整改或索赔。

### 事故三：承诺失控

销售在标书里写"7×24 小时 15 分钟到场""免费提供 3 年驻场工程师"，
中标后发现服务网点根本覆盖不到项目所在地，或三年人力成本远超利润。

> 真实代价：低价中标 + 过度承诺 = 项目亏损。

### 事故四：答非所问

招标问"是否支持国密算法"，方案答了一段"我们高度重视信息安全，采用纵深防御理念"。
评委按评分表找分，找不到就不给分——**你没答，等于没写**。

> 真实代价：技术分被压到及格线以下，明明产品满足却输给对手。

**本技能把这四类事故变成四个可检查的机制**：条目化台账、零发明标记、承诺三档分级、覆盖声明。

## 核心设计：五条铁律

这五条是本技能与"通用写作提示词"的根本区别。

| # | 铁律 | 含义 | 防的事故 |
|---|---|---|---|
| 1 | **条目化**：无编号不落笔 | 招标每条要求都有 `R-XXX` 编号，全文只引用编号 | 漏项 |
| 2 | **零发明**：查不到就标待确认 | 参数/业绩/资质/SLA 一律不编，写 `[待确认: 原因]` | 编造 |
| 3 | **覆盖优先**：先答全，再答好 | 覆盖所有必答项 → 才优化表达 | 漏项 |
| 4 | **结构对齐**：不改招标方骨架 | 章节层级、编号、顺序与招标一致 | 答非所问 |
| 5 | **承诺可控**：不写无权承诺 | 承诺分 A/B/C 三档，C 档需决策人批准 | 承诺失控 |

> 五条铁律的完整定义见 [`SKILL.md`](SKILL.md)。

## 功能特性

### 一、要求抽取与台账

把招标文件变成可勾选、可计数、可追溯的 `requirements.csv`。

- 自动识别章节结构：`第X章`、`1.1`、`2.3.1`、`（一）`、Markdown 标题
- 自动判定强制程度：区分"必须/须/应/不得"（废标项）与"建议/宜/可"（评分项）
- 自动归类：资格 / 格式 / 技术 / 商务 / 服务 / 评分 六类
- 自动标记需澄清的模糊表述（"或同等""原则上""视情况"）
- **防误判处理**：不会把"故障响应时间"的"应"、"投标人须知"的"须"误判为强制词

### 二、章节映射与覆盖门禁

`outline-map.csv` 把每条要求安排到具体章节，形成硬门禁：

- 必答条目未映射章节 → **不允许进入撰写阶段**
- 撰写时每章开头写覆盖声明 `> 覆盖条目：R-005, R-006`
- 校验时反向检查：每条必答是否真的被引用

### 三、反编造规则

六类内容绝对禁止编造，并给出"不确定时怎么写"的三种合法格式：

| 情形 | 写法 |
|---|---|
| 需外部材料确认 | `[待确认: 需原厂 datasheet 确认最大并发数]` |
| 需商务决策 | `[待商务确认: 拟承诺 XX，需批准]` |
| 行业通识、无具体数值 | `[通识表述，需技术确认]` |

配套 `--list-todo` 清单模式，交付前必须清零。

### 四、自动校验

两个纯标准库脚本，无需安装依赖：

```bash
# 有阻断项 → 退出码 1；全部通过 → 退出码 0，可直接接入 CI
python scripts/validate_bid.py --bid ./bid --req requirements.csv --map outline-map.csv \
  --score scoring-matrix.csv --project "本项目名称" --project-no "项目编号" \
  --report validate.json
```

检查 12 项：占位符残留、必答覆盖（区分"声明"与"实质"）、灰色响应表述、章节映射缺失、
章节编号连续性、绝对化表述、注水套话、评分点无证据、复用污染（旧项目名/编号/内部用语）、
docx 不可读、输入异常、篇幅统计。

**其中三项是 v2 才有的**，也是真实项目里最容易"假通过"的地方：

| 检查 | v1 的表现 | v2 的表现 |
|---|---|---|
| 覆盖率 | 章节头写了编号就算覆盖（可被声明行绕过） | 区分声明级/实质级，只有声明直接 `COV-02` 阻断 |
| 引用识别 | `\b` 正则在中文语境失配，覆盖率可能恒为 0 | 改用 lookaround，`条目R-001` 也能识别 |
| docx 缺依赖 | 静默返回 `[跳过]` 并当作正文扫描 | 明确报错，退出码 2 |

### 五、评分作战表（v2 新增）

`scoring-matrix.csv` 把评分办法拆成"得分点 → 分值 → 证据 → 章节 → 把握度"，
一张表回答三个问题：**哪些分确定拿不到、哪些分还没安排落点、满分离我们多远**。

```bash
python scripts/validate_bid.py --bid ./bid --req requirements.csv --score scoring-matrix.csv
```

- 评分点无承载章节 → `SCORE-01` BLOCKER（白丢分）
- 证据列为空 → `SCORE-02` BLOCKER（有分无证据）
- 可达分/理论满分 < 70% → `SCORE-06` 竞争力提示

### 六、方法论文档

不是泛泛的"写作建议"，是可直接执行的判定规则：

| 文档 | 内容 |
|---|---|
| [`requirement-parsing.md`](references/requirement-parsing.md) | 一句话一条要求的判定标准、强制词强度表、五个必拆类别、矛盾处理 |
| [`anti-hallucination.md`](references/anti-hallucination.md) | 六类禁编内容、三种合法写法、`[待确认]` 收敛七步流程 |
| [`writing-style.md`](references/writing-style.md) | 先响应后展开的固定句式、禁用词表、承诺三档分级、篇幅控制 |
| [`scoring-matrix.md`](references/scoring-matrix.md) | 评分办法拆解、得分点作战表、主观分三层拿分逻辑、正偏离纪律 |
| [`compliance-checklist.md`](references/compliance-checklist.md) | 7 部分 60+ 项交付前核对清单，标注高频废标点 |
| [`tech-domains.md`](references/tech-domains.md) | 9 大子系统（网络/机房/服务器存储/安防/音视频/布线/软件/安全/运维）要点与评委常问 |

### 七、模板与示例

## 四种工作模式

v1 的问题是"不管问什么都跑六阶段"，一句话的请求也要走全流程，重且慢。v2 先路由再执行：

| 模式 | 你的一句话 | 走哪些阶段 | 拿到什么 |
|---|---|---|---|
| **M1 读标** | "这标书讲了什么、红线在哪" | S0 → S1 → 解读 | 台账 + 废标红线清单 + 评分点表 |
| **M2 编标** | "帮我写技术标" | S0 → S5 | 八件套 |
| **M3 体检** | "这份标会不会废标" | S0 轻量 → S4 | 核查报告 + 整改清单 |
| **M4 定点** | "这句能不能写" | 单点判断 | 结论 + 原文依据 |

路由口诀：**有现成稿 → M3；只有招标文件 → M1；要成稿 → M2；问一句 → M4。**
模式可以升级，但不默认升级——用户说"那就接着写吧"再进 M2。

## 工作流总览

```
S0 建档          确认输入清单（I1–I8）+ 资格符合性自检（只列缺口，不下"能不能投"的结论）
  │               🚧 G0：无招标文件 / 纯扫描件未 OCR → 停止
  ▼
S1 解析          招标文件 → requirements.csv（R-001 起，15 列，带行号与版本）
  │               去重合并重复条款；产出三个基准数字：原始 / 主条目 / 必答
  │               🚧 G1：条目数明显低于经验值（每 10 页 15–30 条）→ 补抽
  ▼
S1.5 人工修订     修正 mandatory 与 strength、补 owner、整理澄清函
  │               ⚠️ 这一步不能省，脚本只做初判（陈述句形式的强制条款抓不到）
  ▼
S2 映射          requirements → outline-map.csv；评分办法 → scoring-matrix.csv
  │               🚧 G2 硬门禁：必答未映射 / 评分点无章节 → 禁止撰写
  ▼
S3 撰写          逐章推进，每章首部写覆盖声明，首段直接回应原文
  │               不确定处标 [待确认]，不编造；同步做复用污染自检
  ▼
S4 双轨核查      轨一：validate_bid.py 跑 12 项确定性检查（exit 1 = 有阻断）
  │               轨二：compliance-checklist.md 做 A–G 七维语义复核
  │               🚧 G3：BLOCKER 必须清零
  ▼
S5 交付          八件套：正文/台账/映射/评分表/应答表/待确认清单/交付清单/校验报告
                  汇报写清「已完成什么、未完成什么、哪些待确认」
```

> 与 v1 的差别：每个阶段多了**门禁与失败动作**，而不是"做完就往下走"。
> 门禁不过时的正确处理是停下来说明缺什么，不是继续写。

## v2 修了什么

### 一、定位与流程

| 问题（v1） | 后果 | v2 的处理 |
|---|---|---|
| 不管什么请求都跑 S0–S5 | 一句话的请求也要 6 个阶段，用户等不起 | 四模式路由，M1/M3/M4 显著裁剪 |
| 明确"不判断该不该投"，但也不给任何决策材料 | 不合格的项目被一路推进到撰写，白干 | 增加资格符合性自检表（只列缺口，结论留给人） |
| 无信息冲突优先级 | 正文与补遗冲突时随便择一 | 定义五级优先级：补遗 > 正文 > 附件格式 > 口述 > 历史模板 |
| 无版本台账 | 按旧版写作，补遗内容漏响应 | `source_ver` 列 + `clarification-log.csv` |
| 硬门禁只写在 README 流程图里 | 模型可能跳过人工修订直接映射 | 门禁 G0–G3 写进 SKILL.md，并配"停下来说明什么"的话术 |
| 无停止规则 | 遇到缺料/超授权承诺继续往下写 | 六条硬停止规则 H1–H6 |

### 二、脚本（可复现的缺陷）

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | 覆盖率正则用 `\bR-\d{3,}\b` | 中文语境下 `\b` 失配（中文算 `\w`），"条目R-001"匹配不到，覆盖率可能恒为 0 | 改 lookaround，加回归测试 T01 |
| 2 | 覆盖声明行本身也算"引用" | 章节头写 `> 覆盖条目：R-012` 即判通过，正文一字不写也不报错 | 双层覆盖：声明级 vs 实质级，新增 `COV-02` |
| 3 | docx 缺依赖时返回 `[跳过]` 字符串 | 该字符串被当正文参与扫描，结果看起来正常但完全失真 | 抛 `InputError`，退出码 2 |
| 4 | 章节编号只认 Markdown `#` | 真实 .docx 转文本没有 `#`，编号检查恒为空（假通过） | 支持 `第X章` / `# N.` / `N、` 三种体例 |
| 5 | 类型判定"章节优先" | "投标人须知"整章被判资格、"技术要求"整章被判技术 | 句内优先、章节兜底；评标/合同章节作强信号 |
| 6 | 无去重 | 同一要求写三遍就被算成 3 条必答，覆盖率永远算不准 | 完全重复/子集/相似度 ≥0.90 三类合并，写 `dup_of` |
| 7 | `source_quote` 与 `requirement` 同源 | 号称"原文溯源"其实没有独立位置 | 新增 `line_no` + `source_ver`，抽查 30 秒可定位 |
| 8 | 输入错误 `sys.exit("字符串")` | 实际退出码 1，与文档写的 2 不符，CI 判错 | 统一 `return 2`，加测试 T09 |
| 9 | 映射表 `chapter` 为空不报错 | 等于"有安排但没落点"，仍算通过 | `MAP-02` 判 BLOCKER |
| 10 | `--list-todo` 与主流程统计口径不一致 | 两处数字对不上，难以向人解释 | 统一取同一份台账口径 |

### 三、新增能力

- **评分作战表**：`scoring-matrix.csv` + `SCORE-01..06`，把"能拿多少分"从口号变成表
- **复用污染扫描**：`POLL-01..03`，查旧项目名/编号/内部用语——比凭空编造更危险的编造变体
- **机器可读报告**：`--report validate.json`，每条发现带 `id/rule/location/evidence/suggestion`
- **交付契约**：固定目录、命名、JSON schema、Issue ID 规则（`references/delivery-contract.md`）
- **异常边界表**：14 种真实情况（扫描件、加密、超长、联合体、电子标、涉密…）的处理口径
- **回归测试**：`tests/test_scripts.py` 23 项，零依赖，每个用例对应一个真实 bug

## 安装

### 方式一：作为 Skill 使用（Claude Code / WorkBuddy / Cursor）

把整个目录放到用户级 skills 目录：

```bash
# Windows
mv ai-bid-document "%USERPROFILE%\.workbuddy\skills\"

# macOS / Linux
mv ai-bid-document ~/.workbuddy/skills/
```

重启助手后，提到"投标 / 标书 / 招标文件 / 应答表 / 偏离表"等关键词时会自动加载。

需要放在项目内共享时，改放到 `{项目目录}/.workbuddy/skills/`。

### 方式二：脱离 AI 当工具用

只需要 Python 3.8+，无第三方依赖：

```bash
git clone https://github.com/Jackon-Li/ai-bid-document.git
cd ai-bid-document
python scripts/extract_requirements.py --help
```

读取 `.docx` 需额外安装（可选）：

```bash
pip install python-docx
```


看到这样的输出就成功了：

```
生成条目数 : 22
必答(Y)    : 17   非必答(N): 5

  资格: 4    格式: 3    技术: 5    商务: 4    服务: 3    评分: 3
```

**第 2 步：人工修订台账（关键，不能跳）**

打开 `requirements.csv`，重点改三件事：

1. 把陈述句形式的强制条款改成 `mandatory=Y`
   （如"合同签订后60日内交货"没有情态动词，脚本抓不到）
2. 把评分项从 `Y` 改回 `N`（不满足不废标，只是少得分）
3. 补齐 `owner` 列，每条都要有责任人

改完记住两个数字：**总条目数 / 必答数**。这是后面所有覆盖率计算的基准。

**第 3 步：写章节映射**

复制 `templates/outline-map.csv`，为每条必答安排章节。

**第 4 步：撰写时随时查待确认项**

```bash
python scripts/validate_bid.py --bid ./bid --list-todo
```

**第 5 步：交付前校验**

```bash
python scripts/validate_bid.py --bid ./bid --req requirements.csv \
  --map outline-map.csv --score scoring-matrix.csv \
  --project "本项目名称" --project-no "KM-2026-1234" \
  --report validate.json
```

`exit 0` 才可交付。看到 `exit 1` 就按报告逐项清零；输入有问题时返回 `exit 2`。

**第 6 步（可选）：跑一遍回归测试，确认脚本在你机器上的行为一致**

```bash
python -m unittest discover -s tests -v      # 23 项，无需安装任何依赖
```

## 两份核心台账

整个方法的地基是两张表。理解这两张表，就理解了这个技能。

### 1. `requirements.csv` — 要求台账

**作用**：回答"招标方到底要求了多少件事，每件是什么"。

| 字段 | 含义 | 为什么重要 |
|---|---|---|
| `req_id` | `R-001` 起的唯一编号 | 后续所有引用、核对、校验都靠它 |
| `section` | 来源章节 | 追溯时能立刻翻回原文位置 |
| `requirement` | 要求正文 | 写作时的直接依据 |
| `type` | 资格/格式/技术/商务/服务/评分 | 决定由谁负责、怎么响应 |
| `mandatory` | `Y` = 不满足即废标 | **最高优先级字段**，判错代价最大 |
| `source_quote` | 原文摘录 | 复核时逐字对照，防止改写走样 |
| `response_type` | 响应/偏离/证明/承诺 | 决定这一条在标书里以什么形式出现 |
| `need_clarify` | `Y` = 需发澄清函 | 把模糊要求变确定要求的唯一机会 |
| `strength` | 禁止/必须/应/宜/可 | 强制强度五级，决定整改优先级（v2 新增） |
| `source_ver` | `v1`/`补遗-01` | 出自哪一版文件，防止按旧版写作（v2 新增） |
| `line_no` | 整数 | 原文行号，30 秒定位原文（v2 新增） |
| `dup_of` | `R-00X` 或空 | 与哪条重复；只有空值计入必答数（v2 新增） |
| `owner` / `status` | 人名 / 待响应… | 多人协作时不至于互相等 |

### 2. `outline-map.csv` — 章节映射

**作用**：回答"每条要求安排在哪一章答"。

| 字段 | 含义 |
|---|---|
| `req_id` | 对应要求 |
| `chapter` | 章节号（如 `3.2`） |
| `chapter_title` | 章节名称 |
| `primary` | `Y` = 主应答章节（一条要求可有多处提及，但只有一个主应答） |
| `evidence_needed` | 需要的证明材料 |

**它是硬门禁**：存在未映射的必答条目时，不允许开始撰写。
因为"边写边想放哪"是漏项的主要成因。

## 适用场景

### ✅ 强烈建议使用

| 场景 | 为什么适合 |
|---|---|
| **系统集成项目投标** | 子系统多、要求分散、格式要求繁杂，正是条目化的用武之地 |
| **政府/国企采购投标** | 资格与符合性审查严格，废标风险高，格式清单价值最大 |
| **技术标撰写** | 需逐条对应评分表，"先响应后展开"直接提升主观分 |
| **点对点应答表 / 偏离表编制** | 三值规范（完全响应/部分响应/不响应）避免灰色表述 |
| **多轮投标 / 复用历史标书** | 台账可沉淀为组织资产，下次直接改 |
| **多人协作投标** | 台账带 owner 与 status，交接不丢信息 |
| **投标文件复核** | 已有稿件直接跑校验，快速发现漏项与占位符残留 |
| **用 AI 辅助写标书** | 反编造规则正是 AI 最需要的外部约束 |

### ⚠️ 需要调整后使用

| 场景 | 需要注意 |
|---|---|
| **货物类纯采购**（无实施） | 技术方案权重低，重点放在应答表与偏离表，可跳过 S3 的大段撰写 |
| **服务类采购**（咨询/外包） | 需补充"人员投入测算""服务方法论"相关内容 |
| **工程类招标**（施工） | 本技能偏 IT 集成，工程量清单、施工组织设计需另配专业模板 |
| **国际招标 / 英文标书** | 词表为中文招标文件设计，英文需替换 `STRONG_PATTERNS` 等词表 |

明确说明边界，避免误用：

| 不适用 | 原因 |

## 设计思路

几处刻意的取舍，说明为什么这样设计：

### 为什么不直接让 AI 写整份标书？

因为 AI 最擅长的是"生成流畅文本"，而投标最怕的正是"流畅但不可靠"。
一份 200 页的 AI 生成标书，人工复核成本可能高于自己写——
你要核对每个数字、每个案例、每个承诺。

所以本技能把 AI 放在**该在的位置**：做机械的抽取、归类、校验、格式转换，
把判断留给人。这也是 `mandatory` 判定必须人工复核的原因。

### 为什么强制"条目化"而不能直接对段落？

因为**段落无法计数**。你无法回答"这版比上版多覆盖了几个要求"，
也无法在交接时说"还有 3 条没答"。
编号把模糊的"应该写得差不多了"变成明确的"17/18 已覆盖，R-019 缺"。

### 为什么校验脚本只查形式？

因为语义级检查（答非所问、数值方向错误）误报率极高，
一个天天误报的工具会被弃用。
所以脚本只做**确定性检查**——占位符、覆盖率、编号、词表，
把语义判断交给 `compliance-checklist.md` 的人工流程。

**脚本管形式，清单管实质。** 两者都不能省。

### 为什么把"承诺"单独分级？

因为投标文件是**要约文件**，写入即产生法律约束。
技术人员写方案时容易把"我们能做"写成"我们承诺无条件做到"，
而这两者在合同上的分量完全不同。
三档分级（A 可自主 / B 需部门核定 / C 需决策人批准）把这个问题前置到写作时解决，
而不是等中标后发现承诺无法履约。

## 常见问题

**Q：这套方法适合小项目吗？会不会太重？**

A：项目越小，资格与符合性要求占比越高，反而越不能漏。但可以简化：
只做 `requirements.csv` + 跑 `validate_bid.py`，跳过 mapping 与完整清单。
核心是"条目化 + 校验"，其余可按需取用。

**Q：抽取出来的条目太多，几百条怎么办？**

A：正常。真实招标文件 60 页通常 100–300 条要求。
关键是**必答（mandatory=Y）的条数**，那才是硬约束，通常只占 40%–60%。

**Q：脚本判定错了怎么办？**

A：改 CSV。脚本只是初稿工具，`requirements.csv` 是活文档，
人工修订后的版本才是准的。修订记录建议写进 `note` 列。

**Q：能让 AI 直接把整份标书写完吗？**

A：技术上可以，但**不建议直接交付**。
合理用法：AI 按章节起草 → 人工核对每个数字与承诺 → 脚本校验形式 → 清单核对实质。
把 AI 当"高速打字员 + 结构检查员"，不当"决策者"。

**Q：没有评分办法怎么办？**

A：S2 只做章节映射，跳过得分点作战表。
但强烈建议向招标方索取或从招标文件中找——**没有评分办法，等于闭着眼睛写方案**。

**Q：`[待确认]` 太多，来不及收敛怎么办？**

A：两条路：① 优先收敛 `mandatory=Y` 条目里的标记（这些影响废标）；
② 实在无法确认的，**删去该表述改写为不含承诺的写法**，而不是带标记交付。
带标记交付等于把内部问题暴露给评委。

## 局限与免责

**必须明确认知的局限**

1. **脚本不能替代判断**。覆盖率 100% 不代表答得好，只代表"提到了"。
2. **词表为中文招标文件设计**，其他语种需自行替换。
3. **不处理扫描件**。图片型招标文件需先 OCR。
4. **不校验法律条款**。违约责任、知识产权归属等须法务确认。
5. **模板与示例中的项目、参数、编号均为虚构**，不得直接引用。

**免责声明**

本技能提供的是**写作方法与检查工具**，不构成法律、商务或合规建议。
投标文件的法律后果由投标人及其签署人承担。

使用本技能不代表获得任何项目的投标资格或使用授权。
涉及渗透测试、安全评估类项目时，须确保已获得目标方的书面授权。

**明确拒绝的用途**：伪造资质证书、编造业绩案例、代签代盖章、规避招标程序。
