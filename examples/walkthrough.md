# 完整走一遍：从招标文件到可交付稿件

本文用一个**虚构但贴近真实**的案例，把 S0→S5 全流程演示一遍。
每一步都给出可复制的命令与真实输出，你可以直接照做。

---

## 场景设定

某市"智慧园区视频监控升级项目"，招标文件约 60 页。你拿到的是 `招标文件.txt`。

| 项 | 内容 |
|---|---|
| 项目 | 智慧园区视频监控升级 |
| 招标内容 | 前端点位扩容 + 平台升级 + 3 年运维 |
| 我们 | 系统集成商，代理某品牌视频平台 |
| 截止 | 12 天后 |

对照 `templates/delivery-checklist.md` 的「输入材料到位情况」，逐项打勾：

|---|---|---|

## S1.5 人工修订：这一步不能省

**脚本给出的 `mandatory` 只是初判，必须人工过。** 本例要改三处：

### 改动 1：R-010 应从 N 改为 Y

原文「合同签订后60个日历日内完成全部设备到货」是**陈述句**，没有"应/须/必须"，
脚本抓不到强制语气。但它在**商务条款**章，是硬性工期要求。

```
改前: R-010 | 商务 | N
改后: R-010 | 商务 | Y   note=工期硬约束，超期即违约
```

### 改动 2：R-021 应从 Y 改为 N

原文「类似项目业绩每提供1个得2分，最多得8分」——脚本因为"最多"判定为强制。
但这是**评分规则**，不是门槛项，不满足不废标，只是少得分。

```
改前: R-021 | 评分 | Y
改后: R-021 | 评分 | N   note=评分项，非门槛
```

### 改动 3：补 owner

每条都要有责任人。没有责任人的条目，等于没人管。

```
R-001~R-004 → 商务部
R-005~R-009 → 技术部
R-010~R-013 → 商务部
R-014~R-016 → 服务部
R-017~R-019 → 投标组
R-020~R-022 → 商务决策人
```

修订后的基准数字：**总条目 22 / 必答 18**。
这个数字要写进交付清单——它是后面所有"全覆盖"说法的唯一依据。

按 `templates/outline-map.csv` 建表：

| req_id | chapter | chapter_title | primary | evidence_needed |
|---|---|---|---|---|

**硬门禁检查**：18 条必答，是否有任何一条没有 `chapter`？

```bash
python scripts/validate_bid.py --bid ./bid --req requirements.csv --map outline-map.csv
```

若输出「章节映射缺失」，说明有条目还没安排位置——**此时不要动笔写，先补映射**。

## S3 撰写：每个章节先写覆盖声明

技术方案第 2 章开头的写法（照此格式）：

```markdown
# 第2章 技术方案

> 覆盖条目：R-005, R-006, R-007, R-008, R-009

## 2.1 视频接入能力

我方平台单机支持 [待确认: 需原厂 datasheet 确认最大接入路数] 路视频接入，
满足并优于招标文件第二章 2.1 条「不少于 2000 路」的要求。
平台已通过 GB/T 28181 标准符合性检测，证书编号见附件四。

...
```

三个要点：

1. **首段直接回应**：「满足并优于……要求」——评委一眼看到响应；
2. **不确定就标记**：接入路数未拿到 datasheet，写 `[待确认]`，不猜；
3. **留落点**：`（完全响应 R-005）` 让校验脚本能定位，也让人能追溯。

> 反面写法（常见）：
> 「随着智慧城市建设的深入推进，视频监控作为重要的感知手段，其重要性日益凸显……」
> ——写了 300 字还没提 2000 路，评委找不到，直接不给分。

## S4 校验：跑脚本

```bash
python scripts/validate_bid.py --bid ./bid --req requirements.csv --map outline-map.csv
```

典型输出（故意留了三处问题）：

```
【统计】
  · 必答覆盖率：94.1%（16/18）
  · 篇幅：1 个文件 / 97 行 / 1213 字符 / 量化表述 13 处
────────────────────────────────────────────────
【阻断项 BLOCKER】共 3 处 —— 必须清零后才能交付

  ▼ 占位符残留（1 处）
    - [待确认标记] bid-draft.md:31  系统支持 SM2/SM3/SM4 国密算法，
      商用密码产品认证证书 [待确认: 需安全部提供证书编号]（响应 R-007）。

  ▼ 必答条目未覆盖（1 处）
    - R-019 [格式] 投标函须按招标文件第六章提供的格式填写，不得自行改动。

  ▼ 灰色响应表述（易被判不响应）（1 处）
    - [基本满足] bid-draft.md:35  平台具备良好的可扩展性，
      未来可平滑扩容（基本满足 R-008）。

【提示 WARN】共 2 处
  ▼ 一级章节跳号（1 处）
    - bid-draft.md 一级章节跳号：第 3 章 → 第 5 章（缺 1 章）
  ▼ 绝对化表述（1 处）
    - [100%] bid-draft.md:67  承诺 100% 问题当日解决（响应 R-014）

结论：不通过 ✗
```

### 三处 BLOCKER 的处理

| 问题 | 错误做法 | 正确做法 |
|---|---|---|
| `[待确认: 证书编号]` | 随便编一个编号 | 向安全部要证书，或改写为"证书见附件四"，附件必须真的存在 |
| R-019 未覆盖 | 不管，觉得格式项不重要 | 在 6.3 节补写投标函响应——**这是废标项** |
| 「基本满足」 | 保留，觉得比"不满足"好 | 改「完全响应」。灰色表述会被评审判为不响应，比承认偏离更糟 |

### WARN 的处理

- 章节跳号 → 检查是否漏写了第 4 章（本项目是"实施与组织方案"，**必须写**，不能跳）；
- `100% 问题当日解决` → 这是绝对化承诺，**未经决策人批准不得写入**，改为"按 SLA 约定时限处理"。

## 用了 vs 没用：差别在哪

| 维度 | 不用本技能 | 用本技能 |
|---|---|---|
| 漏项 | 靠人通读，10 页后开始疲劳 | 覆盖率可量化，漏一条就报错 |
| 参数 | 不确定时"先写个差不多的" | 强制标 `[待确认]`，编造无处藏身 |
| 承诺 | 销售一句话，标书里就敢写"终身免费" | 三档分级，无授权不落笔 |
| 结构 | 模板套用，章节与招标不对应 | 按招标骨架，映射表兜底 |
| 复核 | "再看一遍吧" | 脚本 + 清单，有明确通过标准 |
| 交接 | 换人接手，不知道写到哪了 | 台账显示每条的责任人与状态 |

**最实际的一条**：招标文件 60 页，人工抽取要求约需 4 小时且容易漏；
脚本跑一遍 3 秒出 22 条，人工只需核对修订，约 40 分钟。
省下的时间用在"怎么答得更好"上，而不是"有没有漏"上。
